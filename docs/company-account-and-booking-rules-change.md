# 公司帳號與實際借車規則調整規格

更新日期：2026-08-08  
適用專案：M365 公務車借用自動通知與後台管理流程  
文件狀態：需求確認完成，待功能調整與測試驗證

## 一、文件目的

本文件彙整公司帳號基本功能、實際公務車借用方式及最新確認的營運規則，並與原有系統設計比較，列出必須調整或新增的規則、功能及測試項目。

後續 Power Automate、SharePoint、Teams Adaptive Card、循環預約處理、測試計畫及操作文件，均應以本文件為最新業務規則依據。

## 二、公司帳號與使用範圍

| 項目 | 原有規則／狀態 | 新確認規則 | 系統調整 |
|---|---|---|---|
| 使用者範圍 | 未明確限定 | 僅公司內部正式員工 | 排除外部帳號、Guest、私人信箱及跨租戶情境 |
| 預約帳號 | 借用人來源主要取 Organizer | 借用人本人使用公司帳號建立 | 通知對象固定取預約建立者本人 |
| Microsoft 365 功能 | 曾將無 Teams、帳號異常列為可能問題 | 全員具備 Outlook、Teams、個人聊天及 Adaptive Card 功能 | 無須將一般帳號缺少 Teams 功能列為上線驗收項目 |
| 帳號生命週期 | 未明確 | 離職、停權、改名及 Email 由 IT 統一管理 | 系統不處理離職帳號繼續預約的正常流程 |
| Teams 使用環境 | 未明確 | Windows、網頁、iPhone、Android 均會使用 | 四種用戶端各完成一次卡片驗收 |
| SharePoint 使用者 | 未明確 | 僅承辦人與管理員 | 管理功能及立即同步按鈕只授權指定群組 |

## 三、Outlook 借車方式

| 項目 | 原有規則／狀態 | 新確認規則 | 系統調整 |
|---|---|---|---|
| 預約方式 | 文件包含直接操作資源行事曆的測試 | 借用人建立 Outlook 活動，於「新增會議室／位置」選擇公務車 | 正式測試必須使用真實借用入口 |
| 代訂 | 未明確 | 不允許代訂，必須由借用人本人建立 | 排除主管、助理或同事代訂情境 |
| 預約成立條件 | 以資源行事曆存在事件為主 | 資源信箱接受後才成立 | 被拒絕的預約不得建檔或發卡 |
| 同車衝突 | 系統另外偵測並標記異常 | 資源信箱會自動拒絕衝突預約 | FT-113 降為防禦性測試，不作為正常流程主要門檻 |
| 同一人借多台車 | 可能被視為異常 | 允許同日或同時借不同車輛 | 不得因借用人相同而阻擋 |
| 單筆日期範圍 | 未完全限制 | 一筆預約只代表一天 | 排除單筆跨日及單筆多日事件 |
| 換車 | 可能視為原事件的車輛異動 | 取消原預約，再建立新車預約 | 新車預約視為全新借用，重新建檔與發卡 |

## 四、共乘人數規則

| 項目 | 原有規則／狀態 | 新確認規則 | 系統調整 |
|---|---|---|---|
| 人數定義 | 未明確 | 共乘人數包含駕駛 | Card 及操作文件需明確標示 |
| 上限 | 可能依車輛容量判斷 | 不限制最高填寫人數 | 不做座位數上限驗證 |
| 必填 | 必填 | 維持必填 | Card 前端及流程後端都要驗證 |
| 合法值 | 只驗證未填不可送出 | 應為非負整數 | 增加零、負數、小數、文字及空白測試 |

Teams Adaptive Card 欄位建議由「共乘人數」改為：

```text
乘車總人數（含駕駛）
```

## 五、一般通知規則

| 情境 | 原有規則 | 新規則 |
|---|---|---|
| 一般借用 | 借用前 1 小時通知 | 維持 |
| 最早通知時間 | 不早於借用當日 08:00 | 僅適用 08:00 以後的借用 |
| 提前 20～60 分鐘建立 | 沒有明確規則 | 同步完成後立即發卡 |
| 距離開始不足 20 分鐘 | 仍可能由排程補發 | 不發卡，轉臨時借用 |
| 建立時借用已開始 | 可能漏同步或事後補發 | 不發卡，轉臨時借用 |
| 借用人未回覆 | 曾可能每 5 分鐘重複發送 | 不重複提醒，由承辦人在領鑰前處理 |
| Card 有效期限 | 未限制至借用開始 | 借用開始時間一到立即失效 |

## 六、08:00 前借用規則

原規則：

```text
07:30 借用
→ 預計通知時間為當日 08:00
```

此規則會造成借用開始後才發卡，已不符合最新營運需求。

新規則：

```text
借用開始時間早於 08:00
→ 不發 Teams Card
→ 由承辦人人工確認
→ 通知狀態＝不需通知
```

調整要求：

- FT-106 原本的「07:30 借用、08:00 發卡」測試規則廢止。
- 系統不得設定晚於借用開始時間的有效通知。
- 08:00 前借用直接標記 `通知狀態＝不需通知`，避免排程事後補發。

## 七、臨時借用規則

### 7.1 臨時借用定義

符合任一條件即判定為臨時借用：

- 建立時距離借用開始不足 20 分鐘。
- 建立時借用已經開始。
- 借用開始時間早於 08:00。

### 7.2 處理規則

1. Outlook 預約仍由借用人本人建立。
2. 資源信箱接受後才算成立。
3. SharePoint 仍需建立正式借用紀錄。
4. 不發 Teams Card。
5. `通知狀態＝不需通知`。
6. 承辦人透過電話、當面或 Email 確認。
7. 承辦人於 SharePoint 填寫乘車總人數、規範確認狀態、領鑰狀態及承辦人備註。
8. 承辦人備註應記錄確認方式及時間。
9. `Teams 回覆時間` 不得用來假裝 Teams 回覆；人工確認時維持空白。
10. 系統不得在取車後補發無確認意義的 Card。

## 八、SharePoint 立即同步功能

### 8.1 原有狀態

- 正式流程每 15 分鐘同步三台車。
- 臨時預約無法保證立即出現在 SharePoint。

### 8.2 新增功能

SharePoint 管理頁新增：

```text
立即同步三台公務車
```

功能要求：

- 一次同步 Altis、Camry、Cross。
- 承辦人按下後 60 秒內完成。
- 承辦人不需切換到 Power Automate。
- 顯示執行中、成功或失敗。
- 顯示新增、更新、取消及異常筆數。
- 顯示同步完成時間。
- 執行期間停用按鈕，避免連續點擊。
- 重複執行不得建立重複 SharePoint 紀錄。
- 僅承辦人及管理員可操作。

建議介面：

1. 優先實測 SharePoint 頁面內嵌 Power Apps 同步面板。
2. 前置條件為確認公司 O365 E1 租戶是否允許承辦人執行內嵌 Power Apps。
3. 若 Power Apps 不可用，改採 SharePoint 控制清單搭配 Power Automate 按鈕。

## 九、Graph 查詢時間窗調整

### 9.1 原有問題

目前 Graph 查詢主要使用：

```text
start/dateTime >= utcNow()
```

若借用人於 10:05 建立一筆 10:00 開始的預約，下一次同步時事件開始時間已早於 `utcNow()`，可能永遠不會進入 SharePoint。

### 9.2 新規則

同步必須涵蓋近期已開始、尚未結束或剛建立／修改的事件。

建議查詢時間窗：

```text
開始：目前時間往前 24 小時
結束：目前時間往後 14 天
```

處理要求：

- 以 Event ID／iCalUId 防止重複。
- 支援已開始事件及臨時事件同步。
- 支援近期修改事件重新同步。
- Graph 空結果、失敗或回傳不完整時，不得直接執行取消判定。
- 增加查詢窗口起點、終點及時區邊界測試。

## 十、Card 到期與失效提示

### 10.1 新增到期條件

卡片回覆前增加：

```text
目前時間 < 借用開始時間
```

若借用已開始：

- 不更新 SharePoint。
- 不寫入乘車總人數。
- 不寫入規範確認。
- 不變更領鑰狀態。
- 顯示：

```text
此公務車借用已開始，確認卡已失效。請聯絡公務車承辦人完成確認後，再辦理領取鑰匙。
```

### 10.2 失效原因提示

| 原因 | 提示內容 |
|---|---|
| 已開始 | 此公務車借用已開始，確認卡已失效 |
| 已完成確認 | 此借用已完成確認，請勿重複送出 |
| 已取消 | 此借用已取消，無法再送出確認 |
| 預約內容異動 | 借用資料已更新，請使用最新確認卡 |
| 卡片版本過期 | 此確認卡已失效，請使用最新卡片 |

不得再以同一句「已取消或已變更」涵蓋所有失效原因。

## 十一、時間異動規則

### 11.1 Card 尚未回覆

| 異動後狀態 | 新處理 |
|---|---|
| 距離開始至少 20 分鐘 | 舊卡失效，依新時間發送新卡 |
| 距離開始不足 20 分鐘 | 舊卡失效，不發新卡，轉人工確認 |
| 借用已開始 | 舊卡失效，轉人工確認 |
| 開始時間改為 08:00 前 | 舊卡失效，轉人工確認 |

### 11.2 已完成確認

- 修改開始時間：保留原確認。
- 修改結束時間：保留原確認。
- 乘車總人數維持不變。
- 規範確認維持不變。
- 領鑰狀態維持不變。
- 不重新發卡。
- SharePoint 僅更新最新起訖時間及事件最後修改時間。

原 SG-T05「任何異動都使舊卡失效」須改寫，不能對已完成確認的資料一律重置。

## 十二、循環預約功能

### 12.1 原有狀態

- `/calendar/events` 可能只取得 `seriesMaster`。
- 個別發生實例尚未展開。
- 現有文件已假設可逐日發卡，但底層能力尚未完成驗證。

### 12.2 新確認規則

系統必須支援：

- 每日循環。
- 每週循環。
- 整月循環。
- 數月循環。
- 每一天獨立建立 SharePoint 紀錄。
- 每一天獨立計算通知時間。
- 每一天獨立發送 Card。
- 每一天獨立填寫乘車總人數。
- 每一天獨立確認規範。
- 修改整個系列。
- 取消整個系列。
- 只修改其中一天。
- 只取消其中一天。

### 12.3 資料識別要求

每個循環發生實例至少保存：

- Series Master ID。
- Occurrence Event ID。
- iCalUId。
- 發生日期。
- 原始開始時間。
- 是否為例外事件。
- 系列最後修改時間。

建議實例唯一鍵：

```text
資源信箱 | SeriesMasterId | OccurrenceStartDateTime
```

若 Graph 可取得個別 Occurrence Event ID，則優先使用：

```text
資源信箱 | OccurrenceEventId
```

## 十三、失敗告警功能

### 13.1 告警對象

Graph、SharePoint 或 Teams 流程連續失敗時，同時通知：

- 承辦人 Teams。
- `ad.general@alp.global`。
- `tina.yang@alp.global`。

### 13.2 告警內容

- 流程名稱。
- 發生時間。
- 受影響車輛。
- Flow Run ID。
- 失敗動作。
- 錯誤訊息。
- 是否影響同步或 Teams Card 通知。
- Power Automate 執行紀錄連結。

### 13.3 錯誤防呆

- Graph API 失敗或回傳不完整時，不執行取消判定。
- Teams 發卡失敗時，不得永久停在 `已通知`。
- 發卡失敗應更新為 `通知失敗`，並允許受控重試。
- SharePoint 寫入失敗不得造成下一輪重複發卡。

| 原測試 | 調整內容 |

| FT-108 手動觸發成功發卡 | 增加真實排程、自動發卡及防重複驗證 |
| FT-110 未填人數 | 增加後端空值、負數、小數、文字及零值驗證 |

| SG-T05 異動使舊卡失效 | 拆分為未回覆與已完成確認兩種規則 |
| SG-T06 舊卡防呆 | 增加已開始、已完成、已取消、版本過期等原因 |
| SG-T07 重複觸發 | 原結果撤回，重新驗證 Teams 不重複發送 |

## 十五、可排除的非必要測試

以下情境不列入正式上線功能驗收：

- 外部帳號、Guest、私人信箱及跨租戶。
- 沒有 Outlook、Teams 或 Adaptive Card 授權的員工。
- 使用者自行封鎖 Power Automate Bot。
- 離職帳號繼續預約。
- 共用帳號預約。
- 主管、助理或同事代訂。
- 直接進入資源信箱行事曆建立事件。
- 單筆跨日或多日事件。
- 同一員工同時借不同車輛的阻擋。
- 共乘人數超過座位數。
- 資源信箱拒絕後仍建立申請紀錄。
- 每月超過 1,000 筆的高流量情境。
- 系統重複提醒未回覆使用者。
- 改時間後要求已完成確認者重新填卡。

## 十六、新版正式業務流程

```text
員工本人於 Outlook 建立活動
→ 新增會議室／位置並選擇公務車
→ 資源信箱接受或拒絕
→ 拒絕：流程結束，不建檔
→ 接受：排程同步或承辦人立即同步
→ 展開單次事件或循環每日實例
→ 建立／更新 SharePoint
→ 判斷通知類型
   ├─ 08:00 前借用：不發卡，人工確認
   ├─ 已開始或不足 20 分鐘：不發卡，人工確認
   ├─ 剩餘 20～60 分鐘：立即發卡
   └─ 超過 60 分鐘：借用前 1 小時發卡
→ 卡片於借用開始時間到達後失效
→ 未回覆者由承辦人於領鑰前人工確認
→ 修改時間依是否已完成確認決定重發或保留
→ 取消同步為已取消
→ 換車視為新預約重新執行
```
