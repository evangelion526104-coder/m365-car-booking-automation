# 異常處理說明

更新日期：2026-08-04（對應版本 v0.3.3）

本文件彙整「M365 公務車借用自動通知與後台管理流程」目前已知會發生的異常情境、發生原因與處理方式，供行政／總務承辦人與後續維運人員參考。日常操作請優先參閱 [docs/operation-manual.md](operation-manual.md)；本文件聚焦於「不正常」或「需要人工判斷」的情境。

## 一、SharePoint 標記類異常

### 1. 重複資料檢查結果 = 疑似重複（SG-T09）

**情境**：同一「預約唯一鍵」（資源信箱 + Event ID）在 SharePoint 出現多筆紀錄。正常情況下不應發生，多為人為以 API 直接寫入或極端邊界情況所致。

**系統行為**：所有相符紀錄的「重複資料檢查結果」會被標記為「疑似重複」，「公務車借用前Teams通知與回覆」流程會排除這些紀錄，不發送 Teams 通知。

**處理方式**：承辦人應先確認是否為測試資料或系統異常，必要時聯繫維運人員檢查 Outlook 原始事件與 SharePoint 紀錄是否對應正確，確認無誤後再手動處理（例如刪除多餘的重複紀錄），不得逕行忽略直接發放鑰匙。

### 2. 重複資料檢查結果 = 異常（FT-113，同車時段重疊）

**情境**：同一台車有兩筆（含）以上借用起訖時間重疊的紀錄，例如借用人誤植時間，或同一時段被不同單位重複預約。

**系統行為**：系統不會阻擋建立（保留改期等合理情境的彈性），但會將重疊紀錄的「重複資料檢查結果」標記為「異常」。

**處理方式**：承辦人於發放鑰匙前，應先向借用人或相關單位確認是否為同一台車重疊借用，釐清後才決定是否放行，不得忽略異常標記逕行放行。

### 3. 已知限制：兩種異常標記共用同一欄位

「重複資料檢查結果」欄位目前同時承載 FT-113（時間重疊）與 SG-T09（唯一鍵重複）兩種不同語意的判斷結果。若同一紀錄同時符合兩種異常情境，因流程中「條件」（FT-113）先執行、「條件2」（SG-T09）後執行，僅會保留後執行動作寫入的值，前一判斷結果會被覆蓋而未保留。

**目前影響**：不影響 Teams 通知阻擋邏輯的正確性（只要非「正常」皆會被排除），但承辦人無法單從欄位值判斷該筆紀錄究竟屬於哪一種異常。若需要進一步釐清異常原因，應同時人工比對 Outlook 事件時間與其他同車紀錄。

**建議**：後續版本可評估拆分為獨立欄位（例如「時段重疊檢查結果」與「唯一鍵重複檢查結果」），此為已知限制、非阻擋性 Bug，暫列觀察項目。

## 二、舊 Teams Adaptive Card 相關異常

**情境**：借用人送出的 Adaptive Card 對應的借用事件，已被取消、已完成確認、事件內容已異動，或卡片版本非最新版。

**系統行為**：系統會於借用人送出前重新檢查 SharePoint 最新狀態，任一條件不符即不更新資料，並回覆固定提示：「此借用已取消或已變更，請重新確認最新借用資訊。」

**處理方式**：屬正常防呆行為，無需人工介入。若借用人反映收到此提示但認為資訊應仍有效，請承辦人於 SharePoint 查看該筆紀錄目前狀態，並視情況以「手動確認程序」（見 `docs/admin-manual-confirmation-procedure.md`）協助處理。

## 三、通知未送達或重複發送

**常見原因一（人工操作導致）**：手動編輯 SharePoint 紀錄時，只修改「領鑰狀態」而未同步修改「通知狀態」，導致系統誤判為「未通知」而持續每 5 分鐘重複發送 Teams 卡片；或反向誤判為「已通知」但實際未發送。

**處理方式**：務必依 `docs/admin-manual-confirmation-procedure.md` 所列欄位對照表，手動確認時「同時」更新「領鑰狀態」與「通知狀態」，不得只改其中一項。

**常見原因二（系統性根因，2026-08-06 員工回報後診斷確認）**：即使沒有任何人工誤改欄位，「公務車借用前Teams通知與回覆」流程本身也會在借用人尚未回覆的等候期間重複發送卡片。原因是：

1. 「通知狀態」欄位僅在「張貼調適型卡片並等候回覆」這個會持續等候使用者回覆的動作完成、並通過 SG-T06 防呆後，才由「更新項目」寫回「已通知」。在借用人回覆之前，該欄位仍維持「未通知」。
2. 流程的 Recurrence 觸發程序並未設定並行控制（維持系統預設「允許並行執行」），與「公務車行事曆同步至SharePoint」流程於 v0.2.16 已建立的「並行控制＝1」防護不一致。
3. 因此每 5 分鐘的排程都會啟動一個新的並行執行個體，重新讀到同一筆「未通知」的紀錄並再次符合發送條件，對同一位借用人反覆發送新的卡片，直到對方回覆為止。

**連帶症狀（填寫共乘人數送出後看似無反應）**：當借用人回覆其中一份卡片並成功寫回（領鑰狀態更新為「已完成確認」）後，其餘尚未回覆的重複卡片，會在 SG-T06 防呆檢查「領鑰狀態 ≠ 已完成確認」時判定為過期，導向 False 分支，只回覆一則籠統的「此借用已取消或已變更，請重新確認最新借用資訊。」訊息——內容未反映真正原因（其實是重複卡片、已經確認過），容易被誤以為「送出後沒有反應」。

**目前狀態**：兩個 Power Automate 流程已於 2026-08-06 全部關閉止血，專案仍在測試階段、尚未正式啟用。修正方向已記錄於 `docs/todo.md` P4 第 9 項（發送卡片前即寫入通知狀態作為鎖定、補上觸發程序並行控制＝1、改寫 False 分支提示文字），待修正並驗證通過後才會重新開啟。

## 四、已知限制（尚未修正，非阻擋性）

| 項目 | 說明 | 影響 |
|---|---|---|
| 「通知發送時間」欄位尚未有實際寫入邏輯 | 欄位已存在，但目前僅以「通知狀態」欄位反映是否已通知，未記錄精確發送時間戳 | 不影響通知是否發送的判斷；僅影響稽核時無法精確查詢發送時間點 |
| SharePoint DispForm 顯示畫面偶爾時間顯示疑似疊加時區偏移 | 於 v0.3.2 驗證階段觀察到，重新整理頁面後恢復正常 | 不影響底層資料與流程比對邏輯正確性，屬顯示層觀察項目 |
| 重複資料檢查結果欄位共用（見上方第一節第 3 點） | FT-113 與 SG-T09 共用同一欄位 | 不影響通知排除邏輯，僅影響人工判斷異常原因的效率 |

## 五、流程執行失敗時的排查方式

1. 於 Power Automate「我的流程」開啟對應流程（「公務車行事曆同步至SharePoint」或「公務車借用前Teams通知與回覆」），查看「執行歷程記錄」。
2. 找到失敗的執行紀錄，展開查看是哪一個動作失敗，錯誤訊息通常會指出型別不符、欄位名稱錯誤或連接器逾時等原因。
3. 若為單次暫時性失敗（例如連線逾時），通常下次排程會自動重試，一般無需人工介入。
4. 若為持續性失敗（同一動作連續多次失敗），應保留錯誤訊息與執行 ID，並依 `docs/Project_Workflow.md` 的版本控管規則，於修正後建立新的 commit、更新 CHANGELOG 與 release note。
