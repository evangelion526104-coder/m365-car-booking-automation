本文件彙整針對新規格文件所有差異項目，逐筆與使用者確認後的決策結果。實作前請先確認以下內容無誤。

## 一、帳號與借用方式

| 項目 | 決策 |
|---|---|
| 借用人判斷 | 固定取預約建立者本人，不再以 Organizer 判斷（技術查證後維持用 organizer，見下方補充） |
| 代訂 | 不允許代訂，排除主管/助理/同事代訂情境 |
| 預約成立條件 | 完全信任資源信箱接受/拒絕結果，不另建判斷邏輯 |
| 同車衝突（FT-113） | 降為防禦性測試，正式流程門檻交由資源信箱處理 |
| 換車 | 採「取消舊預約＋建立新預約」，新預約視為全新借用重新建檔發卡 |
| 跨日事件 | 時段型橫跨午夜（如晚借到隔天早上）維持現行邏輯，正常處理 |
| 整天多日事件 | 目前無實際案例，暫不處理，待日後真的發生再設計 |

**技術查證補充（2026-08-27）**：查證 Microsoft Graph `event` 資源官方屬性清單（[learn.microsoft.com/graph/api/resources/event](https://learn.microsoft.com/en-us/graph/api/resources/event)）後確認，`event` 物件並無獨立的 `createdBy` 欄位（僅有 `organizer`，型別為 `Recipient`；相近的 `createdDateTime` 只是時間戳記，不含身分資訊）。因此目前流程程式碼所用的 `organizer` 已是 Graph API 能取得「此行事曆事件由誰建立/寄送」的唯一欄位，無其他技術替代方案。既然「不允許代訂」已是既定業務規則，正常流程下 organizer 即等同預約建立者本人，故此項決策以維持現況（不更動程式碼）結案，不再列為待實作項目。

## 五、循環預約功能（本次最大工作量項目）

**技術驗證結果**（已用 Graph API 實測確認）：
- Office 365 Outlook 連接器（O365 E1 授權）**不支援 `calendarView`**，該端點為 Microsoft 建議的官方展開方式，但不在此連接器允許的物件清單中
- 目前可用的 `/calendar/events?$filter=...` 端點**只會回傳未展開的 seriesMaster 物件**，不會自動展開成每日 occurrence
- 以真實案例（Michael Chiu 平日循環借用）驗證：目前系統只會抓到系列第一天，後續所有工作日借用完全抓不到

**決策**：一次完整實作所有循環類型（每日／每週／整月／數月），需自行解析 Graph 回傳的 `recurrence` 規則物件，在 Power Automate 流程中手動計算每個 occurrence 的日期，逐日建檔與發卡；並支援系列中單日修改／單日取消的同步。
