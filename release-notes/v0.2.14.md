# v0.2.14 - 修正「更新項目」時間欄位 +8 小時位移嚴重錯誤

日期：2026-07-24

## 版本目的

v0.2.13 完成流程首次成功執行驗證後，於 P3 情境測試過程中，透過連續多次 SharePoint REST API 比對，發現一個先前未被發現的嚴重資料正確性錯誤：正式流程「更新項目」（SharePoint Update，PATCH/MERGE）動作，寫入借用起始時間、借用結束時間、預計通知時間、事件最後修改時間時，比「建立項目」（SharePoint Create，POST）動作正確寫入的時間，多了整整 8 小時（恰為 Taipei 時區的 UTC 位移量）。本版本鎖定成因並完成修正與驗證。

## 重要發現：Create 與 Update 對相同運算式的解讀不一致

- 兩個動作對借用起始時間欄位使用的運算式完全相同，皆為：
  `formatDateTime(convertTimeZone(items('套用至各項_1')?['start']?['dateTime'],'UTC','Taipei Standard Time'),'yyyy-MM-ddTHH:mm:ss')`
  即先將 Graph 回傳的 UTC 時間轉換為 Taipei 時間，再輸出成不含時區後綴（無 `Z`、無 UTC 位移量）的字串。
- 以測試紀錄（SharePoint Item Id=4，「測試-P3情境-一般借用」）連續三個時間點比對：
  1. 建立當下（Create 執行）：借用起始時間正確顯示為「2026/7/25 上午 03:00」。
  2. 第一次排程自動觸發「更新項目」後：同一欄位變成「2026/7/25 上午 11:00」（+8 小時）。
  3. 第二次排程自動觸發「更新項目」後：仍維持「上午 11:00」，未再疊加，證實是固定位移、非累積誤差。
- 進一步以「剖析 JSON」動作的原始輸出比對前後兩次執行，確認 Graph 回傳的來源資料（`start.dateTime`）完全相同，排除來源資料變動的可能性。
- 結論：問題不在運算式寫法，而是 SharePoint 連接器的 Create（POST）與 Update（PATCH/MERGE）動作，對「不含時區後綴的模糊時間字串」採用了不同的解讀邏輯——Create 會將其視為「目的地顯示時區的本地時間」並正確反推為 UTC 儲存；Update 則直接將其視為 UTC 儲存，導致再由系統依站台時區轉換顯示時，多加了一次 +8 小時。

## 影響範圍

- 每一筆借用紀錄，只要經過第一次排程自動更新（正式流程每 15 分鐘執行一次），借用起始時間、借用結束時間、預計通知時間就會被錯誤地多加 8 小時；事件最後修改時間亦受相同機制影響。
- 已確認正式（非測試）SharePoint 紀錄 Id=1、Id=2 的 `Modified` 時間皆已對應到會觸發此錯誤的更新執行，惟因兩筆紀錄事發時未取得建立當下的比對基準，僅能以錯誤機制推論其同樣受影響，無法逐筆重新驗證確切位移量。
- 本錯誤直接推翻 `release-notes/v0.2.13.md` 原先「判定：通過」的結論——該結論僅以單次 Create 執行後的資料驗證為依據，尚未涵蓋排程自動觸發的 Update 情境。

## 修正內容

修正範圍限定在「更新項目」動作本身，「建立項目」動作維持原樣不變（因其目前運作正確）：

1. **借用起始時間 / 借用結束時間**：移除 `convertTimeZone(...,'UTC','Taipei Standard Time')` 轉換，改為直接輸出 Graph 原始 UTC 時間並明確加上時區後綴 `Z`：
   `formatDateTime(items('套用至各項_1')?['start']?['dateTime'],'yyyy-MM-ddTHH:mm:ssZ')`（結束時間同理，改參照 `['end']`）。
2. **最後同步時間**：同樣移除不必要的 Taipei 轉換，改為 `formatDateTime(utcNow(),'yyyy-MM-ddTHH:mm:ssZ')`。
3. **事件最後修改時間**：改為 `formatDateTime(items('套用至各項_1')?['lastModifiedDateTime'],'yyyy-MM-ddTHH:mm:ssZ')`。
4. **預計通知時間**：此欄位參照共用的「編輯 1」Compose 動作（`outputs('編輯_1')`），該 Compose 同時被「建立項目」與「更新項目」使用，且 Create 端目前運作正確，故不直接修改 Compose 本身，改為僅在「更新項目」動作參照該輸出時，額外做時區反推＋補上 `Z` 後綴：
   `formatDateTime(addHours(outputs('編輯_1'),-8),'yyyy-MM-ddTHH:mm:ssZ')`
   （`addHours(...,-8)` 將 Compose 輸出的「模糊 Taipei 本地時間字串」換算回真正的 UTC 時刻，再以明確 `Z` 後綴輸出，交由 Update 動作正確寫入。）
5. 明確加上 `Z` 時區後綴後，SharePoint Update（PATCH/MERGE）即能正確判讀來源為 UTC，不再套用錯誤的二次轉換。

## 驗證方式與結果

1. 修正五個欄位後儲存流程，確認「您的流程已準備就緒」，零錯誤。
2. 手動觸發測試執行（此時測試紀錄 Id=4 已存在，故會走「更新項目」分支）。
3. 執行後立即以 SharePoint REST API（`FieldValuesAsText`）查詢 Item Id=4，確認：
   - 借用起始時間：「2026/7/25 上午 03:00」（修正前為錯誤的「上午 11:00」）
   - 借用結束時間：「2026/7/25 上午 04:00」（修正前為錯誤的「上午 12:00」）
   - 預計通知時間：「2026/7/25 上午 08:00」（修正前為錯誤的「下午 04:00」）
   - 三者皆與 Create 當下的原始正確值一致，確認 Update 路徑的 +8 小時錯誤已解除。

## 判定

- 「更新項目」動作的時間欄位 +8 小時位移錯誤，判定為**已修正並驗證通過**。
- `release-notes/v0.2.13.md` 的「判定：通過」結論需以本版本補充修正：v0.2.13 當時僅驗證了 Create 路徑，Update 路徑的資料正確性直到本版本才完整驗證。
- 正式（非測試）紀錄 Id=1、Id=2 過去因走過 Update 路徑而被寫入錯誤時間；已於下次排程自動更新後重新查詢確認，兩筆紀錄的時間欄位皆已回復正確（詳見下方「追加驗證」段落），確認修正對既有正式資料同樣有效。
