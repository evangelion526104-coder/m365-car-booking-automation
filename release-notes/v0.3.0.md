# v0.3.0 - P2 公務車借用前 Teams 通知與回覆流程完成並驗證通過

日期：2026-07-29

## 版本目的

v0.2.16 完成 P1 階段（正式行事曆同步流程清理、正式化切換與 Concurrency Control）後，下一步是進入 P2 階段：建立「公務車借用前 Teams 通知與回覆」流程，讓借用人於借用前收到 Teams Adaptive Card 通知，並在回覆後將共乘人數、規範確認等資訊寫回 SharePoint，同時具備 SG-T06 舊卡片防呆能力。本版本完成流程建置、修正過程中發現的多項 Bug，並以真實 Teams 卡片來回驗證 FT-108～FT-111 與 SG-T06 正向、負向兩條路徑。

## 本次處理內容

### 一、建立「公務車借用前Teams通知與回覆」流程

新建流程（Flow ID `8187f981-d4a8-4ca5-89a7-684f69c278f5`），動作結構：

`Recurrence（5 分鐘）→ 取得多個項目（讀取全部借用紀錄，無篩選）→ Apply to each → 條件（8 項 AND 判斷是否需通知：通知狀態≠已通知、已取消=false、已失效=false、事件同步狀態=有效、預計通知時間≤utcNow()、領鑰狀態≠已領鑰、通知狀態≠不需通知、重複資料檢查結果=正常）→ True：張貼調適型卡片並等候回覆 → 剖析 JSON → 取得項目（以卡片回傳的 sharePointItemId 重新讀取該筆記錄最新狀態）→ 條件1（SG-T06 舊卡片防呆，8 項 AND 判斷式）→ True：更新項目（共乘人數、規範確認狀態、領鑰狀態=已完成確認、通知狀態、Teams 回覆時間）／False：在聊天室或管道中張貼訊息（固定提示文字）`

Adaptive Card 內容包含車輛名稱、借用日期、借用時間、使用事由與公務車使用規範提示文字，並以「共乘人數」（必填數字欄位）與「我已閱讀並同意遵守公務車使用管理規範」（必勾選核取方塊）作為送出前的卡片端驗證，確保資料不完整時無法送出（對應 FT-110、FT-111）。

### 二、修正「取得項目」action 的 `id` 參數 null 值 Bug

流程開發初期，「取得項目」（重新讀取記錄最新狀態）在特定情境下因 `id` 參數傳入 `null` 導致執行失敗。已修正其參照來源，確保穩定以 `剖析 JSON` 輸出的 `sharePointItemId` 作為查詢依據。

### 三、實作 SG-T06 舊卡片防呆邏輯（條件1）

條件1 比對 Adaptive Card 回覆資料（卡片送出當下的快照：eventId、iCalUId、cardVersion 等）與使用者實際送出當下、重新讀取到的 SharePoint 最新記錄，8 項判斷式全部相符才視為卡片仍然有效：

・ `eventId` 相符
・ `iCalUId` 相符
・ `cardVersion` 相符
・ 事件同步狀態 = 有效
・ 領鑰狀態 ≠ 已完成確認
・ 領鑰狀態 ≠ 已領鑰
・ 領鑰狀態 ≠ 已失效
・ （其餘防呆比對項）

實作過程中發現並修正兩類 Bug：

・ **語法錯誤**：多個判斷式的運算式缺少 `@` 前綴（未被當作運算式解析，而是存成純文字字串），以及括號存取子誤寫為單一字串鍵值（例如 `?['body/OData_xxx/Value']`）而非正確的鏈式括號存取（`?['body']?['OData_xxx']?['Value']`）。此類錯誤延續前一階段已知模式，逐列以「程式碼檢視」比對修正。
・ **型別不一致（本版本新發現、耗時最長的問題）**：語法修正完成、8 列判斷式在「程式碼檢視」中皆確認格式正確後，手動測試仍發現條件1 對一筆全新且有效的卡片回覆判定為 `false`，導致誤觸發 SG-T06 拒絕訊息。逐欄比對 `剖析 JSON` 與 `取得項目` 的原始輸出後定位根因：Adaptive Card 的 Parse JSON 綱要將 `cardVersion` 宣告為**字串**型別，而 SharePoint「卡片版本」欄位是**數字**型別，其 OData 原始值為未加引號的數字；Power Automate 的 `equals()` 比較字串與數字時，即使數值相同也恆回傳 `false`。修正方式為將該判斷式兩側都以 `string()` 包裝（`@string(body('剖析_JSON')?['cardVersion'])` 對 `@string(outputs('取得項目')?['body']?['OData__x5361__x7247__x7248__x672c_'])`），確保比較不受底層欄位型別影響。

### 四、其餘動作串接

・ 條件1 True 分支：更新項目寫回 `共乘人數`、`規範確認狀態`、`領鑰狀態 = 已完成確認`、`通知狀態`、`Teams 回覆時間`（`utcNow()`）。
・ 條件1 False 分支：張貼固定提示文字「此借用已取消或已變更，請重新確認最新借用資訊。」，不寫入 SharePoint。

## 驗證方式與結果

・ **FT-108**：手動觸發流程，確認測試借用人（tina.yang@alp.global）於 Teams 收到借用確認卡片，內容含車輛、借用日期、借用時間、使用事由與規範提示，格式正確。
・ **FT-109～FT-111**：借用人於卡片填入共乘人數並勾選規範確認後送出；以 SharePoint REST API 直接查詢確認記錄正確更新：`領鑰狀態 = 已完成確認`、`共乘人數 = 3`、`規範確認狀態 = true`、`通知狀態 = 已通知`，並寫入 `Teams 回覆時間` 時間戳記。共乘人數與規範確認皆為卡片端必填/必勾選欄位，未完整填寫時卡片無法送出，等同確保 SharePoint 不會被不完整資料覆蓋。
・ **SG-T06 正向路徑**：借用人於卡片資料與目前 SharePoint 記錄完全一致的情況下回覆，條件1 執行結果顯示 `expressionResult: true`（真分支執行、假分支「0 動作」），SharePoint 正確更新為已完成確認。
・ **SG-T06 負向路徑**：在借用人回覆前，人為將測試記錄的「行事曆事件 ID」由 `TEST-P2-EVENTID-001` 改為 `TEST-P2-EVENTID-001-CHANGED`，模擬 Outlook 端事件已異動、卡片資料已過期；借用人回覆後，條件1 執行結果顯示 `expressionResult: false`，Teams 正確顯示「此借用已取消或已變更，請重新確認最新借用資訊。」；以 SharePoint REST API 直接查詢確認 `領鑰狀態` 仍維持異動前的 `待通知`、`Modified` 時間戳記停留在人為異動當下，證實「更新項目」動作確實未被執行。

## 已知限制與待驗證事項

・ **操作疏失記錄**：進行 SG-T06 負向測試前重設測試記錄狀態時，僅重設了「領鑰狀態」而遺漏「通知狀態」，導致主要「條件」判斷式（要求通知狀態≠已通知）仍為 `false`，流程未能送出新卡片；同時因記錄一直維持在符合主要條件觸發狀態，背景 Recurrence 每 5 分鐘重複對同一筆測試記錄送出新卡片給借用人，直到將記錄的「領鑰狀態」與「事件同步狀態」皆設為終止狀態（取消／已取消）並取消所有等待回覆中的重複執行個體後才排除。後續測試建議：重設多個「應代表同一狀態」的欄位時，應建立完整清單逐一核對，避免遺漏導致條件判斷不一致。
・ 「通知發送時間」欄位目前尚未有實際寫入邏輯，僅以「通知狀態」欄位反映是否已通知。
・ FT-104～FT-107（09:30／08:30／早於 08:00／整天借用之預計通知時間規則）、FT-112（承辦人後台依領鑰狀態判斷發鑰）、FT-113（同車重複預約）、SG-T08（Event ID 唯一鍵）、SG-T09（重複資料異常）等測試案例尚待執行。
・ 沿用先前版本已記錄的已知限制：SharePoint 篩選查詢日期比較字串未明確加註 UTC 標記，不影響正確性判定。
