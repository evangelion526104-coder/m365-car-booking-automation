# v0.2.15 - 新增事件取消偵測補強邏輯並驗證通過

日期：2026-07-27

## 版本目的

v0.2.14 追加更新的 P3 情境測試發現一個架構缺口：正式流程「公務車行事曆同步至SharePoint」從未包含「偵測 Outlook 事件消失」的比對步驟——流程每次執行只處理「本次讀取到的事件」，若某筆 SharePoint 紀錄對應的 Outlook 事件被刪除或取消，流程無從得知，SharePoint 紀錄會永遠停留在刪除前的最後狀態（`已取消 = 否`），後續 Teams 通知也不會停止（FT-103／SG-T04）。本版本設計並實作「事件取消偵測」補強邏輯，完成後手動觸發驗證通過。

## 修正設計

在既有流程「套用至各項」（逐台車）迴圈內，內層「套用至各項 1」（逐筆事件）迴圈結束後，新增以下動作鏈：

1. **初始化變數** `CurrentEventKeys`（陣列，於外層迴圈之前建立，每台車進入迴圈時以「設定變數」重設為空陣列）：追蹤「本次執行實際讀取到」的所有事件唯一鍵（`資源信箱|Event ID`）。
2. **附加至陣列變數**：內層事件迴圈每處理一筆事件，將其唯一鍵（`outputs('編輯')`）附加進 `CurrentEventKeys`。
3. **取得多個項目 1**（SharePoint Get items，新增）：篩選「該車輛」且「未取消」且「借用起始時間」落在與本次行事曆讀取相同的時間窗（`utcNow()` 至 `addDays(utcNow(),14)`）內的既有紀錄——確保只檢查與本次讀取範圍可比對的資料，避免誤判時間窗以外的正常未來借用。
4. **套用至各項 2**（逐筆檢查前一步取得的既有紀錄）：
   - **條件 1**：`contains(variables('CurrentEventKeys'), items('套用至各項_2')?['OData__x9810__x7d04__x552f__x4e00__x93'])` 等於 `false`，即該筆既有紀錄的唯一鍵未出現在本次讀取結果中，代表對應的 Outlook 事件已消失。
   - **真分支**：**更新項目 1**（SharePoint Update）：僅更新 `已取消 = 是`、`事件同步狀態 = 已取消`、`取消時間 = utcNow()`，不觸碰其餘欄位。

## 實作過程中的技術細節

- SharePoint 欄位內部名稱經 REST API（`/_api/web/lists(...)/fields`）逐一核對，確認 `預約唯一鍵` 對應 `OData__x9810__x7d04__x552f__x4e00__x93`（因欄位顯示名稱過長，SharePoint 內部名稱本身即為截斷後的 32 字元編碼，屬正常現象，非本次新增錯誤）。
- Power Automate 新設計工具的運算式編輯器（fx）出現一個已知 UI 缺陷：手動直接輸入語法正確的運算式（例如 `utcNow()`、`contains(...)`）有時會顯示「此運算式有問題」的假錯誤；改用「動態內容」分頁的選取器插入相同運算式（或插入後點擊一次編輯框觸發重新驗證）即可正常通過，不影響流程實際運作。
- 巢狀 Apply to each 迴圈中，Power Automate 動態內容選取器會自動使用 `items('套用至各項_2')` 語法取代舊式 `item()` 語法，兩者功能相同，前者為目前建議寫法。

## 驗證方式與結果

1. 儲存流程，確認「您的流程已準備就緒」，零錯誤。
2. 驗證前先以 SharePoint REST API 記錄基準狀態：Id=1（已取消=否）、Id=2（已取消=否）、Id=3（已取消=否）、Id=4（已取消=否，其 Outlook 來源事件已於先前測試階段被刪除，作為既知的可重現測試案例）。
3. 手動觸發流程執行，執行成功（「測試成功」）。
4. 執行後以 SharePoint REST API 重新查詢，結果：
   - **Id=4**（既定測試案例）：`已取消` 由 `false` 變為 `true`，`事件同步狀態` 由 `有效` 變為 `已取消`，`取消時間` 寫入本次執行時間，符合預期。
   - **Id=1**（Michael Chiu 測試驗證紀錄）：同樣被標記為 `已取消 = true`。經查詢 Power Automate 執行追蹤紀錄，確認 Altis 車輛本次 Graph API 行事曆查詢（`GET /calendar/events?$filter=start/dateTime ge ... and start/dateTime le ...`）回傳結果為空（0 筆事件），並直接以 Outlook 網頁行事曆檢視確認 2026-07-27 全天 Altis 資源信箱行事曆確實無任何事件——證實 Id=1 對應的 Outlook 事件也已被刪除（屬先前測試階段遺留、非本次新發現的異常），偵測邏輯正確識別並標記，屬於**正確判定**而非誤判。
   - **Id=2、Id=3**（Andy Yang、Leo Li，未來合法借用）：`已取消` 維持 `false`，`事件同步狀態` 維持 `有效`，未受影響，證實偵測邏輯不會誤判仍然有效的未來借用。
5. 補充驗證：SharePoint「取得多個項目 1」的篩選查詢中，時間比較字串（如 `2026-07-27T04:33:58`）未附加 `Z` 後綴，經比對執行追蹤紀錄，SharePoint 端的比較行為與 Graph API 端（`start/dateTime ge '...Z'` 明確 UTC）存在數小時的解讀落差，但因此次篩選窗口刻意設計為「檢查範圍應大於或等於行事曆讀取範圍」（寧可多檢查、不可少檢查），此落差不會造成漏檢，僅可能使極少數邊界情況下的紀錄被提前納入檢查（仍會依 `CurrentEventKeys` 正確比對），不影響正確性判定。

## 判定

- 事件取消偵測補強邏輯，判定為**已實作並驗證通過**。
- FT-103／SG-T04（Outlook 取消預約）狀態由「未通過」更新為「通過」。
- 本次驗證額外發現並正確處理一筆先前測試階段遺留、未被追蹤到的孤兒紀錄（Id=1），佐證此補強邏輯具備偵測任意時間點資料飄移的能力，不僅限於刻意建立的測試案例。

## 已知限制與待驗證事項

1. 「取得多個項目 1」篩選查詢的日期比較字串未明確加註 UTC 標記（`Z` 後綴），與 Graph API 端的解讀基準不完全一致；因設計上採用「寧可多檢查」原則，實務上不影響本次驗證結果，但建議於未來版本一併統一為明確 UTC 格式，避免解讀歧義累積成他處問題。
2. 尚未涵蓋車輛、主旨、借用人異動與舊卡片失效機制（`test-cases/function-test-plan.md` SG-T05 其餘部分、SG-T06），待 Teams Adaptive Card 流程開發後一併測試。
3. `是否測試資料` 目前仍為 `是`，待端到端測試通過後再切換。
4. 尚未建立 Concurrency Control。
5. 暫存測試流程 `公務車功能測試-郵件動作參數檢查(可刪除)` 尚未刪除。
