# v0.3.3 - SG-T09 重複資料異常標記補強邏輯完成並驗證通過

更新日期：2026-08-04

## 背景

v0.3.1、v0.3.2 皆將 SG-T09（重複資料異常測試——人為建立相同 `預約唯一鍵` 之多筆資料，驗證系統是否正確標記重複異常且不發送 Teams 通知）列為尚待實際執行的待辦事項。本版本完成該補強邏輯之設計、實作、Bug 修正與端到端驗證。

## 本次新增完成內容

### 補強邏輯設計與實作

* 於「公務車行事曆同步至SharePoint」流程中，在既有「取得多個項目」（以 `預約唯一鍵` 查詢既有紀錄，用於判斷新增或更新）之後，新增「條件2」：比對該查詢結果筆數是否大於 1。
* 若大於 1（表示同一 `預約唯一鍵` 存在多筆紀錄），透過「套用至各項3」逐筆處理所有相符紀錄，並以「更新項目2」將每筆紀錄的 `重複資料檢查結果` 欄位標記為 `疑似重複`。

### 發現並修正三處運算式雙重跳脫 Bug

* 初次儲存並手動觸發測試後，流程於執行期發生 `InvalidTemplate` 錯誤：`'greater' expects two parameter of matching types... invoked with values of type 'String' and 'Integer'`。
* 診斷發現：條件2 比較左值 `length(body('取得多個項目')?['value'])` 被存成純文字字串，缺少代表「這是一段運算式」的 `@` 前綴，導致設計時流程檢查（零錯誤）無法攔截、但執行期因型別不符而失敗。
* 進一步比對後發現套用至各項3 的 `foreach` 來源、更新項目2 的識別碼參數，皆存在同類但相反的問題——被誤存為 `@@{...}`（雙重跳脫：多一層不必要的 `@{}` 包裹），而非正確的 `@...`（單一 `@`，直接取得結果本身而非字串化文字）。
* 根因研判：於 Power Automate 分類設計工具（classic designer）中，直接以鍵盤輸入 `@` 開頭的運算式文字，容易觸發動態內容選取器並造成輸入內容錯亂；改於新版設計工具（v3）以「插入運算式」流程編輯時，若欄位為空且直接鍵入純函式文字（不含 `@`），雖可正常儲存但仍非運算式（僅為字串常值）；需額外清空欄位後改以帶 `@` 前綴的寫法重新輸入，並以唯讀「程式碼檢視」比對既有正常運作動作（如 FT-113 用之「條件」）的相同語法作為基準，確認雙引號內容完全一致後才視為修正成功。
* 三處修正後格式：
  * 條件2：`"@length(body('取得多個項目')?['value'])"` 大於 `1`。
  * 套用至各項3：`foreach` 為 `"@body('取得多個項目')?['value']"`。
  * 更新項目2：識別碼為 `"@items('套用至各項_3')?['ID']"`。

### 發現並修正更新項目2 誤寫入欄位的資料污染風險

* 於逐一比對更新項目2 完整參數時，發現該動作除正確欲寫入的 `重複資料檢查結果` 外，還誤將 `已取消`、`已失效` 兩個防呆欄位強制寫入 `true`，並以固定字串覆蓋 `車輛名稱`、`規範確認狀態`、`領鑰狀態`、`是否測試資料`、`功能測試結果`、`是否整天` 等六個與重複標記完全無關的欄位。
* 研判為由既有事件取消偵測用途的「更新項目」動作複製而來，複製後未清除多餘欄位設定所致。若未修正，正式上線後任何一筆被判定為重複的紀錄，都會被連帶誤標記為已取消、已失效，並覆蓋其車輛、領鑰狀態等真實資料，屬嚴重程度較高的隱性風險。
* 修正：於「進階參數」逐一移除六個無關欄位，修正後更新項目2 僅保留識別碼與 `重複資料檢查結果` 兩個參數，確保只更新本次真正要標記的欄位。
* 流程儲存確認零錯誤（「您的流程已準備就緒」）。

### 端到端驗證

* 第一次手動觸發測試（此時 SharePoint 僅有一筆對應紀錄 TEST-SGT09-A）：流程成功執行完畢，條件2 正確評估為假（筆數未大於 1），確認修正後的運算式於執行期不再拋出型別錯誤。
* 以 SharePoint REST API 查詢 TEST-SGT09-A（ID 19）之完整 `預約唯一鍵` 值（Outlook Event ID 為 Base64 編碼長字串），並以相同鍵值透過 REST API 直接建立第二筆人為重複紀錄 TEST-SGT09-B（ID 21），避免透過 SharePoint 表單手動複製貼上長字串時可能發生的截斷或誤植風險。
* 再次手動觸發流程，以 REST API 查詢兩筆紀錄最終狀態，確認 ID 19、ID 21 的 `重複資料檢查結果` 皆已正確更新為 `疑似重複`，SG-T09 核心判定邏輯驗證通過。
* 驗證過程中另發現 ID 21 的 `已取消`、`已失效` 欄位顯示為 `true`，經追查既有「條件」（FT-113／SG-02 既有 upsert 邏輯）之「更新項目」動作程式碼，確認該動作以 `first(body('取得多個項目')?['value'])?['ID']` 僅更新第一筆相符紀錄（即 ID 19），且明確將 `已取消`、`已失效` 寫入 `false`，並未被本次修改影響；ID 21 的 `true` 值純粹是本次以 REST API 建立測試資料時未指定該兩欄位、沿用 SharePoint 清單欄位預設值所致，屬測試資料本身的既有狀態，非流程邏輯錯誤，不影響 SG-T09 判定結果。

### 複核 Teams 通知流程排除邏輯

* 複核「公務車借用前Teams通知與回覆」流程既有 8 項條件式之程式碼，確認其中一項為 `equals(重複資料檢查結果, "正常")`（相等比對，非白名單排除法）。
* 此寫法代表 `疑似重複`、`異常`（FT-113 沿用同一欄位）或任何非 `正常` 之值，皆會使該條件式為假，排除於發送 Teams 通知對象之外——確認符合 SG-T09「不發送 Teams 通知」要求，無需修改通知流程本身。

## 已知限制與待辦

* `重複資料檢查結果` 欄位目前同時承載 FT-113（時間重疊，寫入 `異常`）與 SG-T09（唯一鍵重複，寫入 `疑似重複`）兩種不同語意的判斷結果。若同一紀錄同時符合兩種異常情境，由於「條件」（FT-113）先執行、「條件2」（SG-T09）後執行，僅會保留後執行動作寫入的值，前一判斷結果會被覆蓋而未保留。因通知流程僅需判斷「是否等於正常」，不影響通知阻擋邏輯正確性，暫列為觀察項目，非阻擋性 Bug，建議後續版本評估拆分為獨立欄位。
